# Repository runtime migration

Use `test-e2e/infra/scripts/run-suite.py` for planning and candidate batch orchestration. `bootstrap`, `run` and `daily` are dry-run unless `--execute` is supplied. Keep the validated external Daily operational until same-commit/same-assets execution and report parity pass. Do not enable GitHub schedules or switch Ubuntu merely because offline runner tests passed.

The repository owns test behavior and prerequisites. Put explicit asset families and optional D4 groups under `preparation` in the Case's `execution.yaml`, validated by `infra/schemas/preparation.schema.json`. An empty family list explicitly declares that no family factory is needed; it must not substitute for missing dependency analysis. Do not require a script hash approval or refresh prerequisite review hashes. When changing a Case or script, assess preparation and cleanup together, update affected declarations, validate their structure and factory references, and run the affected preparation-test-cleanup flow. Static validation alone does not prove prerequisites correct. Keep Git SHA/runtime fingerprints for traceability and migration hashes as comparison evidence, not prerequisite approval gates.

Machine-local `config/pipeline.yaml` owns only timeouts, notification opt-in and explicit build/deploy/preflight argv hooks. It must not become another source of Case definitions or preparation logic. Secrets, fixed resource IDs and local paths stay out of Case scripts. New settings require a schema and safe example. Existing helpers still load users, models, assets and secrets from the selected test home.

The candidate runner must account for every selected Case, distinguish blocked/retired/policy-skipped outcomes from PASS, finalize local reports after interruption, and preserve per-case evidence. A failing independent Case does not prevent unrelated Cases from running. Common configuration and runtime safety may stop a batch; unavailable local toolchains and known-Case execution declarations block only affected Cases. Doctor checks common readiness by default; explicit doctor --full includes dependency diagnostics, not an all-or-nothing business prerequisite. Pending recovery stops business Cases until environment safety is verified. The next scheduled Daily may restore a validated Local configuration backup, synchronize develop and redeploy under the Daily/checkout locks; it must preserve the old evidence and pass service/mode checks before ordinary Cases. Business recovery Cases and historical Case-result files do not gate that redeploy. Active owners/locks, unsafe configuration backups and pending D5 fault recovery remain hard stops. Targeted runs/resume do not bypass recovery. See [daily-validation.md](../../../../test-e2e/infra/tools/docs/daily-validation.md#retrying-a-failed-deployment).

Daily never generates candidates, edits Excel or YAML, refreshes manifests, or promotes test assets. Update tests on the product branch. Generated registry/Excel remain read-only views during execution. Enabled terminal notifications cover success, failure and catchable interruption, including preparation failure; complete shared-latest publication is a separate decision. Uncertain delivery is not automatically retried.

Before claiming runtime migration complete, verify: locked Python/Node dependency closure, controlled HTTP/MCP services, per-case preparation declarations and behavior, isolated deployment, timeout cleanup/recovery, same-version resume, D1-D5 live runs, failure evidence and D6/report/notification parity. Consult `test-e2e/infra/migration/runtime-migration-status.md` for current gaps rather than assuming they are implemented.
