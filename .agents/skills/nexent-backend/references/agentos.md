# AgentOS service boundary

AgentOS lets Management and Runtime deploy independently while sharing a versioned, typed capability contract. The existing services host the client and server endpoints. The protocol carries serializable resource and model bindings, scoped inputs, run state, and events over signed HTTP/JSON and SSE. Runtime resolves authorized references and builds local SDK objects. Keep live SDK instances, local workspace paths, and execution credentials out of prepared run payloads.

- Define shared operations, payloads, and events under `backend/contracts/`. Reuse `infrastructure/agentos_client.py` and `infrastructure/agentos_identity.py` for transport and signing. Trace the app-specific caller through `backend/management/clients/agentos.py` to the mounted Runtime endpoint, or trace a Runtime callback to its Management handler. The receiver verifies service identity and checks the user, tenant, run, and resource scope before executing the operation.
- Management authorizes resources, compiles prepared requests, and owns public conversation writes and event projection. Runtime validates and executes prepared requests, owns run state and its event journal, and exposes run and stream operations. For public conversation changes, trace `backend/management/services/agent/prepared_turn.py`, the Runtime endpoint, and Management's projection path. Use explicit operations for both directions. For example, Runtime calls back for an authorized Management-owned draft write instead of opening Management's repository.
- For persistent runs, preserve the submission key and run ID across retries. Preserve the operation contracts for admission, terminal state, stop, and cursor replay, and keep message projection idempotent. Keep replay of existing events distinct from execution or product actions that start another run. Use [Thread lifecycle](thread-lifecycle.md) for request-owned stream cleanup.
- Use the [AgentOS interface documentation](../../../../docs/agentos.md) for implemented operations, identity, and errors. It points to the `four-service-runtime-decoupling` SPEC for architecture intent. Confirm an operation exists in the current code before using a planned capability.
