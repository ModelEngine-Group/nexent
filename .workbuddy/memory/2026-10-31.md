## execution.py 冲突的完整逻辑分析（14:33-14:40）
- **两侧对同一函数 `_stream_agent_chunks` 的改动本质**：
  - **hotfix（#4264+#4271）加了 4 件事**：
    1. 函数内建 `ExecutionHistory`（read_persisted=lambda→`load_execution_result_content`），挂到 `agent_run_info.observer.execution_history`
    2. 流处理时：`bind_execution_result_unit` 把 execution_result 单元登记进历史（带 key/unit_index）；final_answer 事件记录 `complete_answer_event`
    3. 收尾新增 `final_answer_mode == "complete"` 分支：从 buffered_units 重投影出完整根答案（`complete_answer_content`），覆盖 `final_answer_content`；complete 模式下 message 缺失视为 failed
    4. 落库成功后 `execution_history.mark_persisted(message_id, unit_indexes)`
  - **develop（#4242+#4160）重构成 3 件事**：
    1. 新参数 `execution_state: BackgroundExecutionState`（automation 后台运行状态机），消息创建/失败经 `execution_state.create_assistant/fail` 上报
    2. **落库整体抽成 `finalize_assistant_projection(...)` 返回 projection 协程**（persistence.py），execution_state 存在时经 `settle_background_projection` 结算；`persist_assistant_run_batch` 作为 `persist_batch` 参数注入，**内部调用与 hotfix 手写的完全一致**（同样参数、同样 remove_answer_only_steps/_finalize_buffered_unit_fragments/失败置 failed）
    3. 取消/异常路径挂到 execution_state（AUTOMATION_ARTIFACT_FAILED 等错误码）
- **关键结论（合并可行性）**：两侧落库逻辑**语义同源**——develop 的 `finalize_assistant_projection` 就是从 hotfix 手写的那段抽出来的。合并的正确姿势：**以 develop 结构为骨架**，只把 hotfix 的 4 件事插入对应位置：
  - `complete_answer_event/content` 计算 → 插在 `projection = finalize_assistant_projection(...)` **之前**（它决定 final_answer_content 初值）
  - `ExecutionHistory` 构造 + observer 挂载 → 函数开头缓冲区初始化处
  - `bind_execution_result_unit` → 主循环处理 chunk 处（照搬 hotfix）
  - `mark_persisted` → projection 结算成功后（`settle_background_projection`/`await projection` 之后、persistence_failed 判断之前）
  - `final_answer_mode` 参数 → 签名加一行，与 execution_state 并列
  - `persistence_failed = (final_answer_mode=="complete" and streaming_message_id is None ...)` → 插在 projection 构造前（develop 的 channel=None 提前解析后）
  - 注意 develop 的 projection 内部已做 `remove_answer_only_steps`+final_answer_content 重取，hotfix 的 complete 覆盖逻辑要放在 projection 参数 `final_answer_content=` 传入处（先算 complete 再传）
