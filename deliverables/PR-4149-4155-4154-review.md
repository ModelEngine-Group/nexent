# 一、PR #4149 — AIDP graph_search 与 jargon_coverage

## 1. 变更目的与范围

AIDP 侧已支持 `graph_search` 检索方式与 `jargon_coverage` 重排模式，但 Nexent 的三层校验把这两个值挡在外面。本 PR 是一次**纯枚举扩列**，改动点：

| 层 | 文件 | 改动 |
| --- | --- | --- |
| SDK 校验（managed） | `aidp_search_tool.py` | `_VALID_SEARCH_METHODS` / `_VALID_RERANK_MODES` 加值 + 参数描述 |
| SDK 校验（independent） | `ind_aidp_search_tool.py` | 同上（独立维护一份副本） |
| 后端白名单 | `mount.py` | `search_method` / `rerank_mode` / `reranking_mode` 三处加值 |
| 前端常量 | `const/agentConfig.ts` | `aidp_search.search_method` / `reranking_mode` |
| 前端表单 | `KnowledgeRetrievalParamsForm.tsx` | 两个 Select 的 options |
| Mock | `aidp_mgmt_mock_server.py` | `FusionSearchRequest` 的 `Literal` |

范围克制：出站 payload 的键名、默认值、`hybrid_search` 语义、DB schema 全部不动，无迁移。✅

## 2. 关键逻辑正确性

**✅ 各层枚举值一致**。我逐个核对了 6 个文件的字面量，`graph_search` 与 `jargon_coverage` 拼写完全一致，没有出现 `graphSearch` / `jargon-coverage` 这类变体。

**✅ 白名单三处都改了**。`mount.py` L46-49 同时更新了 `search_method`、`rerank_mode`、`reranking_mode` —— 这点很关键，因为后端有两个不同的参数名（`rerank_mode` 与 `reranking_mode`）在不同工具上使用，只改一个会漏。

**✅ 前端两个入口都覆盖**。`KnowledgeRetrievalParamsForm`（agent 知识库检索 + 会话知识范围两处复用）和 `const/agentConfig.ts`（工具配置弹窗）都加了值。

**✅ 向后兼容**。默认值仍是 `hybrid_search` / `performance`，既有 Agent 配置里存的旧值不会失效。

## 3. 缺陷与遗漏

### 🟡 A1. `ind_aidp_search` 的 UI 下拉缺配置，会退化成自由文本输入

**位置**：
- `frontend/const/agentConfig.ts` **L127-139**（`TOOL_PARAM_OPTIONS` 只定义了 `aidp_search`）
- `frontend/app/[locale]/agents/components/capability/tool/ToolConfigModal.tsx` **L1998**

```ts

```

`IndependentAidpSearchTool` 的 `name = "ind_aidp_search"`（`ind_aidp_search_tool.py` L82），但 `TOOL_PARAM_OPTIONS` 里**没有 `ind_aidp_search` 这个 key**，`getToolParamOptions` 返回 `undefined`（`agentConfig.ts` L149 `if (!toolOptions) return undefined`），于是 `isSelectType = false`，`search_method` / `reranking_mode` 渲染成普通 `Input` 文本框而不是下拉。

（若 UI 上确实不需要这个工具的可选集，则应在 PR 描述里澄清“仅 SDK 层支持，UI 不提供”，避免读者误判。）

### 🟡 A2. 两个工具对非法值的处理语义不一致

| 工具 | 非法 `search_method` | 代码位置 |

**建议**：

### 🟡 A3. 新枚举值零测试覆盖

### 💭 A4. 枚举在 6 处重复定义，无单一事实来源

同一个枚举现在写在了 6 个地方（两个 SDK 工具各自维护 set + 描述字符串、后端白名单、前端常量、前端表单 options、mock Literal）。本次六个点都改对了，但这是**靠人工一致性**维持的。

### 💭 A5. `jargon_coverage` 无中文释义

`aidp_search_tool.py` L138-141 的 `description_zh` 写的是 `"重排序模式：performance/high_accuracy/jargon_coverage"` —— 只是罗列英文枚举，没有像同文件 `search_method` 那样给中文注释（`hybrid_search（融合检索）`）。

**建议**：补 `jargon_coverage（行话覆盖度重排）`，与同文件风格一致。

## 3. 需要指出的技术细节

### 💭 C1. 字体顺序与声称的「基准」相反

PR 描述说对齐“智能体配置页表单的字体基准”，但基准位置 `agents/[agentId]/agent-config.tsx` **L476** 写的是：

```ts
fontFamily: '"Huawei Sans", "HarmonyOS Sans SC", system-ui, sans-serif'
```

**Huawei Sans 优先**。而本 PR 三处写的是：

```ts
fontFamily: "'HarmonyOS Sans SC', 'Huawei Sans', sans-serif"
```

**HarmonyOS 优先**，且丢了 `system-ui` 兜底。严格来说两者渲染结果可能不同：在同时装了 Huawei Sans 和 HarmonyOS 的环境里，基准页用 Huawei Sans，MCP 弹窗用 HarmonyOS。

考虑到本 PR 的目标是“让 placeholder 与其他输入框一致”，**顺序应与基准严格一致**。建议改为：

```ts
fontFamily: "'Huawei Sans', 'HarmonyOS Sans SC', system-ui, sans-serif"
```

### 💭 C2. `HarmonyOS Sans SC` 在这三个弹窗里其实没有 `@font-face` 注册

我检查了全库所有 CSS 文件，`@font-face` 只出现在 3 个 module：

```
newchat/assistant-ui/newchat-design.module.css   : 3 个
components/resource-picker/ParamDialog.module.css : 2 个
components/resource-picker/ResourcePickerDrawer.module.css : 2 个
```

`styles/globals.css` 与 `layout.tsx` **都没有全局注册 HarmonyOS**。因此在这三个 MCP 弹窗中，`HarmonyOS Sans SC` 会因找不到字体而跳过，实际生效的是 `Huawei Sans`（需用户系统已装）→ 再回退 `sans-serif`。

也就是说：
- 改动**方向正确**（去掉 `monospace` 是必须的，placeholder 用等宽确实突兀）
- 但“与智能体配置页一致”的实际效果**依赖运行环境的系统字体**，在未装 Huawei Sans 的机器上两者都退到通用 sans-serif，视觉上只是“都不等宽”了，谈不上精确一致
- 顺带说明：`fontSize: 12` 保留但同弹窗其他输入框可能是 14px，若目标是完全一致，字号也应复核（本 PR 未动，可能是有意的）

**建议**：如果团队希望 HarmonyOS 真正成为稳定基准，应在 `globals.css` 做全局 `@font-face` 注册（本地 `public/fonts/` 已有 3 个字重的 ttf），而不是靠每个 module 各自注册。这属于独立改进项，不阻塞本 PR。

## 4. 影响现有功能

纯样式，无逻辑变更，无 API/状态/事件改动。风险仅在于字体回退链导致不同环境下观感略有差异（C1/C2）。**不影响功能**。
