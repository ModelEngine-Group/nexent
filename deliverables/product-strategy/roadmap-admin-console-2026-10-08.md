# Nexent 管理面（Admin Console）竞争力提升路线图

- 日期：2026-10-08
- 作者：路径（Roadie）· 路线图规划师
- 范围：Nexent 管理面（多租户/权限/配额/审计/监控/SSO），周期 **2026 Q4 → 2027 Q3（4 个连续季度）**
- 输入：竞品调研报告（竞析）、用户研究报告（瑞思）、资产盘点报告（数析），均为 2026-10-08 版本

## 一、战略前提与定位声明

**当前水位**：L3–L4（数析确认：多租户 + 三层存储配额 + CAS/OAuth SSO + RBAC/DAC 双层 + 邀请状态机均已落地，合计后端 ~5,560 行 + 前端 ~11,700 行）。

**目标水位**：**成为唯一「开箱即 L4、一年内逼近 L5 治理级」的开源 Agent 平台**。竞研结论：没有任何开源免费竞品同时具备多租户 + 完整 RBAC + 配额 + 审计 + SSO；Nexent 已握有多租户、配额、CAS 三张牌，只差审计与计量两张，补齐即完成「开源即企业级管控」的占位。

**路线图主线**（4 季度递进）：

```
2026 Q4「合规基座」→ 2027 Q1「成本治理」→ 2027 Q2「身份与可用性」→ 2027 Q3「架构重构」
   P0 审计+计量埋点      P0/P1 多维配额+FinOps     P1 身份生态+运营级       P2 组件化+自定义角色
   (防守：追平门槛)       (进攻：差异化)            可用性(攻守兼备)         (体验：还技术债)
```

**风险基线提示**（贯穿全程）：当前无大规模企业生产用户反馈，企业诉求部分来自 Commercial Issue 与竞品映射推断。每季度末用社区反馈 + Commercial Issue 增量校准一次优先级（详见各季度「风险」栏）。

## 二、优先级框架

采用 P0/P1/P2 分层 + RICE 评分辅助排序。RICE = (Reach × Impact × Confidence) / Effort，各关键项评分见季度交付表。

| 层级 | 定义 | 本期覆盖项 |
|---|---|---|
| **P0 追平企业级门槛** | 缺失即被金融/医疗/政府场景一票否决的能力 | 全量审计日志（#2189）、token/调用计量、多维配额与预算告警（#2854/#2807） |
| **P1 差异化进攻** | 无开源竞品覆盖、可形成独占心智的能力 | Agent FinOps 成本治理、OIDC + 国产身份生态（企微/钉钉/飞书）、SSO 界面化 |
| **P2 体验与重构** | 不影响选型但影响规模化运营体验与研发效率 | 管理面检索/批量（#3449）、SU 自助（#3413）、UserManageComp 拆分、RBAC 去 SQL 硬编码、统一管理台 |

**排序原则**：P0 先于 P1 先于 P2；但 P2 中「运营级可用性」因用户痛点频率极高（#3449 类 Issue 连发），以「最小切片」方式提前嵌入 2027 Q2，完整重构留 2027 Q3。

## 三、分季度规划

### 2026 Q4 —— 主题：合规基座（审计日志 + 计量埋点）

**季度目标**：关掉挂了 10 个月的 #2189，让企业 IT 管理员能回答「谁、何时、对什么资源、做了什么」；同时为 Q1 的 FinOps 铺好计量数据管道（计量埋点与审计共用一套写入基础设施，必须同期设计）。

**关键交付**：

| 交付项 | 对应模块/Issue | 负责人角色 | RICE | 备注 |
|---|---|---|---|---|
| 审计数据模型 + 全量事件采集 | `audit_service` 重构；新建 `audit_log_t` 表（替代日志文件方案）；覆盖登录/登出、资源 CRUD、权限变更、配置变更四类最小可行事件集 | 后端 | 9×3×0.8/5 ≈ **4.3** | 保留现有 `[SEC_AUDIT]` 日志双写一个过渡版本，便于回滚 |
| 审计查询 API + 管理 UI | 新增审计查询路由（分页/筛选 by 用户/时间/资源类型）；resource-manage 新增「审计」tab | 后端 + 前端 | 同上（合项） | 筛选维度对齐用户研究的最小集 |
| 审计导出与保留策略 | CSV 导出 + 保留期配置（默认 180 天，对齐 Dify 企业版基线） | 后端 | 8×2×0.8/3 ≈ 4.3 | SIEM 外送（webhook）留接口不做实现 |
| Token/调用计量埋点 | `quota_service`/模型调用链路埋点：按租户×用户×Agent×模型记录 token 消耗与调用次数（复用 `user_token_usage_log_t` 或新建计量表） | 后端（平台） | 9×3×0.7/6 ≈ 3.2 | 本季只埋点+落库，不做界面；是 Q1 全部交付的数据前提 |
| 配额模型技术债清理（设计稿） | `tenant_config_t` 中配额 KV → 独立配额表的设计评审（不实施） | 后端（平台） | — | 为 Q1 多维配额铺路 |

**依赖关系**：审计 UI 依赖审计表落地；计量埋点无外部依赖但需与模型调用链路 owner（平台）对齐埋点位置；配额表设计稿依赖计量埋点的维度定义。

**风险**：
1. 埋点位置侵入模型调用热路径，可能引入延迟——用异步批量写入（队列缓冲）规避，验收含性能指标。
2. 审计事件粒度过细则写入量爆炸——按「四类最小事件集」控范围，资源明细级别留 Q3 按需扩展。
3. 企业诉求靠推断——若本季 Commercial Issue 反馈与审计优先级冲突，以提单方反馈为准调整。

**里程碑与验收标准**：
1. #2189 关闭：审计 UI 可按用户/时间/资源筛选查询全量操作记录，支持 CSV 导出（12 月中）。
2. 计量数据覆盖率 ≥ 95%：任意一次 Agent 调用的 token 消耗可在计量表中查到归属（租户/用户/Agent/模型四维）（12 月底）。
3. 埋点对调用链路 P95 延迟增加 < 5ms（压测报告）。

### 2027 Q1 —— 主题：成本治理（多维配额 + Agent FinOps 大盘）

**季度目标**：把配额从「存储字节单维度」升级为「存储 × token × 调用次数」多维体系并补齐预算告警（关掉 #2854/#2807，后者来自商业客户）；上线租户级用量/成本大盘，开辟「Agent 平台 FinOps」差异化叙事（竞研确认：无开源竞品覆盖）。

**关键交付**：

| 交付项 | 对应模块/Issue | 负责人角色 | RICE | 备注 |
|---|---|---|---|---|
| 多维配额引擎 | `quota_service`/`quota_app` 扩展：平台/租户/个人三层 × {存储、token/月、调用次数/月} 矩阵式硬限额；`tenant_config_t` 配额 KV 迁移至独立表（Q4 设计稿实施） | 后端 | 9×3×0.8/8 ≈ **2.7** | 参照 FastGPT 四维 quota 但简化为三维，避免过度设计 |
| 阈值预警与预算告警 | 配额用量达阈值（如 80%/95%）触发告警；通知渠道接入 `notification_app`（站内信）+ webhook | 后端 + 前端 | 9×3×0.8/4 ≈ 5.4 | #2854/#2807 的核心诉求；webhook 为邮件/企微群通知留口 |
| 租户级用量大盘 | `monitoring_app` 从 2 路由扩展：租户活跃用户、Agent 调用量、token 消耗与成本 TopN、按模型分布；前端新增内置监控页（替代纯外链 telemetry） | 后端 + 前端 | 8×3×0.7/6 ≈ 2.8 | 「管理员运营层」可观测性（用户研究痛点 5）；与计量埋点同源 |
| 成本归因初版 | 按模型定价表估算成本，大盘展示租户/用户组/Agent 维度成本 | 后端（平台） | 7×3×0.6/5 ≈ 2.5 | 定价表可配置；不做计费（见 Non-goals） |

**依赖关系**：全部交付依赖 2026 Q4 计量埋点；配额引擎依赖 Q4 配额表设计稿；用量大盘与成本归因依赖计量数据积累 ≥ 1 个完整月。

**风险**：
1. 多维硬限额的「超限行为」策略复杂（拒绝 vs 降级 vs 仅告警）——默认策略做「token/调用类仅告警、存储类保持现有硬限」，把强拦截做成租户级开关。
2. 商业客户对配额语义有私有化定制预期——引擎设计预留租户级策略配置，避免代码分叉。
3. 成本估算依赖外部模型定价维护——定价表开源社区共担维护，标注「估算值」。

**里程碑与验收标准**：
1. #2854、#2807 关闭：管理员可为租户/用户设置 token 与调用次数配额，用量达 80% 阈值时收到站内信 + webhook 告警（3 月中）。
2. FinOps 大盘上线：SU/ADMIN 可查看本租户近 30 天 token 消耗趋势、成本 Top10 用户/Agent（3 月底）。
3. 配额语义回归：现有存储配额行为零回归（自动化测试覆盖三层配额主路径）。

### 2027 Q2 —— 主题：身份纵深 + 运营级可用性

**季度目标**：身份侧从「能配」到「好配」——OIDC 协议补齐 + SSO 界面化配置（免改 .env 免重启），启动国产身份生态（企微/钉钉/飞书扫码，至少落地 1 家）；可用性侧做「最小切片」，把百级用户即暴露的管理面硬伤（检索/批量/SU 自助）修掉，完整重构留给 Q3。

**关键交付**：

| 交付项 | 对应模块/Issue | 负责人角色 | RICE | 备注 |
|---|---|---|---|---|
| OIDC 协议支持 | `cas_app`/`oauth_app` 旁新增 `oidc_app`（或统一 identity 模块）：标准 OIDC Provider 对接 + 属性/角色/租户映射（复用 #3667 的 CAS 映射模式） | 后端 | 7×3×0.7/5 ≈ 2.9 | 企业（外企/国企）最常见身份源，竞品开源版普遍缺失 |
| SSO 界面化配置 | 管理台新增「身份源」配置页：CAS/OAuth/OIDC 的连接参数、角色映射可视化编辑，落库动态生效（替代 .env + 重启） | 后端 + 前端 | 7×3×0.7/6 ≈ 2.5 | 用户研究痛点 4（CAS_ROLE_MAP_JSON 手写 JSON） |
| 国产身份生态（第一期） | 企业微信/钉钉/飞书扫码登录，至少落地 1 家（按 Commercial Issue 需求选型） | 后端 | 6×3×0.6/5 ≈ 2.2 | 形成「国产身份集成最全的开源 Agent 平台」心智的第二步（第一步是已有 CAS） |
| 管理面可用性最小切片 | #3449：租户资源管理页（用户/用户组/邀请码列表）支持检索/筛选/排序 + 用户批量删除/批量改角色；#3413：SU 账号补个人信息页与改密入口 | 前端（后端配合加 list 检索参数） | 8×2×0.9/4 ≈ **3.6** | 验收判据沿用用户研究：1000 用户/50 组规模下常见操作 ≤ 3 次点击 |
| 结构化错误信息 | 模型连通性等高频失败场景，报错含状态码 + 请求路径（替代「连接失败」四字） | 后端 + 前端 | 7×2×0.8/2 ≈ 5.6 | 多篇实测文点名，成本极低收益高 |

**依赖关系**：SSO 界面化依赖 OIDC 模块先定义统一的身份源配置模型；可用性切片依赖后端 list 接口加检索参数（前后端联合排期）；扫码登录依赖选定厂商的开放平台资质申请（提前 1 个月启动）。

**风险**：
1. 身份源配置落库涉及敏感凭据存储——需加密存储方案（可复用平台已有密钥管理），是本季最大安全审查点。
2. 厂商开放平台审核周期不可控——飞书/企微/钉钉资质申请于季初并行启动，验收允许「至少 1 家」弹性。
3. 可用性切片可能与 Q3 组件重构冲突——切片只做行为增强不改组件结构，重构在 Q3 以切片后的组件为基准。

**里程碑与验收标准**：
1. OIDC GA：对接一个标准 Keycloak 实例完成端到端登录 + 角色/租户自动映射，全程界面配置零 .env（6 月中）。
2. #3449、#3413 关闭：100 用户规模演示环境中，管理员定位并删除一个用户 ≤ 3 次交互；SU 可在界面完成改密（6 月底）。
3. 国产扫码登录至少 1 家上线并发布社区公告。

### 2027 Q3 —— 主题：架构重构与治理升级（体验还债 + L5 预研）

**季度目标**：还清管理面技术债（单体组件、RBAC 硬编码、双入口），把「运营级」升级为「可规模化定制级」；同时以自定义角色完成向 L5 的第一块拼图，为 2027 Q4 及以后的商业化切分决策（是否引入 license 分层）提供技术基础。

**关键交付**：

| 交付项 | 对应模块/Issue | 负责人角色 | RICE | 备注 |
|---|---|---|---|---|
| UserManageComp 拆分 | `UserManageComp.tsx`（1,441 行单体）按 tab 拆分为独立组件 + 共享租户上下文；顺手拆 `PersonalKnowledgeBaseCapacity`（1,173 行）| 前端 | 6×2×0.9/5 ≈ 2.2 | 纯重构零行为变更，以 E2E 回归测试护航 |
| RBAC 矩阵数据化 | `role_permission_t` 的 SQL 硬编码 INSERT → 种子迁移机制 + 管理端只读展示权限矩阵；为自定义角色铺路 | 后端 | 6×3×0.6/6 ≈ 1.8 | 自定义角色的前置依赖 |
| 自定义角色（初版） | ADMIN 可基于现有 6 角色派生自定义角色并勾选权限子集（原子权限模型参考 LangBot 18 项 permission 设计） | 后端 + 前端 | 6×3×0.6/8 ≈ 1.4 | L5 拼图第一块；亦是潜在商业杠杆，开源/付费边界待主理人与商业团队决策（见 Non-goals） |
| 统一管理台信息架构 | resource-manage / owner-manage 双入口整合为「组织 · 权限 · 配额 · 审计 · 监控」五合一导航（保持角色可见性差异） | 前端 | 6×2×0.7/6 ≈ 1.4 | 竞研机会 4；配合 Q1 大盘、Q4 审计 tab 的整合收口 |
| 等保/信创合规文档包 | 公开权限模型文档 + REST 端点租户/属主校验自查清单（#3532 类 bug 的系统化防复发）+ 安全自评报告模板 | 平台（文档） | 6×2×0.6/3 ≈ 2.4 | 「安全即卖点」：参照 DifyTap 越权事件后的市场信任缺口反打 |

**依赖关系**：自定义角色依赖 RBAC 矩阵数据化先行；统一管理台依赖 Q1/Q2 的审计 tab、监控页、身份源页都已存在后才能收口；组件拆分无硬依赖，可季内并行。

**风险**：
1. 重构与功能交付争抢容量——本季功能项刻意压到最少（仅自定义角色一项新功能），其余为重构与文档。
2. 自定义角色的权限爆炸组合难以穷举测试——初版限制「只能收窄不能放大」既有角色权限，降低风险面。
3. 统一入口改变管理员肌肉记忆——保留旧路由 301 重定向一个版本周期 + 发布迁移指引。

**里程碑与验收标准**：
1. UserManageComp 拆分完成：单文件 < 300 行，管理面 E2E 回归用例 100% 通过，前端构建时间下降可测量。
2. 自定义角色灰度：内部租户可创建派生角色并正确生效于至少 3 类资源（Agent/知识库/模型）的授权判定。
3. 合规文档包发布：权限校验自查清单覆盖全部管理面 REST 路由并在社区发布。

## 四、Non-goals（本期明确不做）

| 项 | 决策 | 理由 |
|---|---|---|
| **计费/订阅系统（billing）** | 不做 | 竞研显示计费是 SaaS/商业版能力（FastGPT 商业版、n8n Cloud）；Nexent 主打私有化部署，开源侧做计费既无场景（自部署客户不按量付费给平台方）又拖累架构。本期只做「计量 + 成本估算」，把 metering 数据管道建好，未来商业化若需要计费可复用——这正是 Q1 成本归因的设计原则 |
| **组织树/部门层级** | **不纳入本期**（明确决策） | ① 用户研究中 Nexent 侧无任何组织树 Issue，诉求纯靠竞品推断，置信度低；② 竞研确认全行业普遍缺失（7 竞品均无完整组织树），不做不构成竞争劣势；③ 现有 Group + DAC 分组共享已覆盖协作场景约八成；④ 若强行做，涉及 HR 同步、层级权限继承等重投入，挤占已验证的 P0/P1 交付。**重新评估触发条件**：出现 ≥ 2 条带 Commercial 标签的组织树提单，或企业深访（用户研究建议项）证实为采购硬门槛时，纳入 2027 Q4 规划 |
| **行级/字段级数据权限** | 不做 | 用户研究判断为「低频高强度长尾」，Nexent 侧暂无 Issue；等保合规叙事用 Q3 的权限校验自查 + 审计闭环即可支撑初判 |
| **SCIM 用户同步 / CSV 批量导入** | 不做 | 中频诉求，且 Q2 的批量操作已缓解最痛场景；SCIM 协议实现重，留待身份生态第二期 |
| **多环境（dev/staging/prod）治理** | 不做 | Nexent 侧零诉求（用户研究确认为长尾），属 n8n Enterprise 级能力 |
| **SIEM 日志外送实现** | 只留接口 | Q4 审计导出已覆盖 CSV 导出；外送 Datadog/SIEM 是 n8n Business 级卖点，实现留待有 Commercial 需求时启动 |
| **开源/商业版切分（license 边界）** | 不做技术决策 | 属商业策略，需主理人与商业团队专项决策。技术侧原则：本期全部 P0/P1 交付进开源版（支撑「开源即企业级管控」占位），自定义角色（Q3）的付费边界留有切分余地，决策前默认开源 |
| **计费类 SSO 强制 2FA / MFA** | 不做 | n8n Enterprise 级能力；本期身份预算集中于 OIDC + 国产生态，2FA 留 2027 Q4 评估 |

## 六、利益相关者沟通要点

### 6.1 高管版（战略对齐 · 业务影响 · 关键决策）

1. **战略占位**：市面上没有任何开源 Agent 平台同时具备多租户 + 配额 + 审计 + SSO，我们已握三张牌，用一年补齐审计与计量，即锁定「开源即企业级管控」的独占心智，直接承接 Dify 社区版被付费墙劝退的政企客户。
2. **新叙事**：2027 年起以「Agent FinOps」开辟成本治理赛道——无开源竞品覆盖，是潜在的商业化引流入口（FastGPT/n8n 均在付费版验证了付费意愿）。
3. **投入与节奏**：4 个季度，前两季追平门槛（防守），后两季差异化与还债（进攻），无新增 headcount 假设，按后端/前端/平台现有角色排期。
4. **关键决策请求**：① 2027 Q3 自定义角色的开源/付费边界需在 Q2 前决策；② 组织树本期不做，需高管认可「等待真实需求信号再投入」的判断。
5. **风险坦诚**：企业诉求目前部分靠 Commercial Issue 与竞品推断，每季度用真实反馈校准，避免闭门造企业级。

### 6.2 工程版（技术细节 · 时间线 · 依赖）

1. **Q4 双线并进是刻意设计**：审计（audit_log_t 新表 + 四类事件）与计量埋点必须同期动工——两者共用异步写入管道，分开做会返工；埋点侵入模型调用热路径，采用队列缓冲 + 批量落库，验收含 P95 延迟 < 5ms 指标。
2. **技术债清单已排期**：tenant_config_t 配额 KV 迁独立表（Q4 设计/Q1 实施）、UserManageComp 1,441 行拆分（Q3）、RBAC SQL 硬编码数据化（Q3），Q3 是刻意设置的「重构季」，功能负载已压到最低。
3. **关键依赖链**：计量埋点 →（Q1）多维配额/FinOps 大盘；OIDC 模块 →（Q2）SSO 界面化；RBAC 数据化 →（Q3）自定义角色；身份源厂商资质申请需提前 1 个月启动。
4. **兼容与安全红线**：存储配额语义零回归（自动化测试护栏）；身份源凭据落库必须加密；审计先行保留日志文件双写一个版本周期便于回滚。
5. **验收可测**：每季度 2-3 条量化指标（见各季度里程碑），含性能、覆盖率、交互次数等，均可用测试或演示环境复现。

### 6.3 设计版（愿景 · 进度 · 里程碑）

1. **一年后的管理台长什么样**：「组织 · 权限 · 配额 · 审计 · 监控」五合一控制台——管理员打开一个入口就能看清谁在用、花了多少、改过什么、身份从哪来，这是当前所有开源竞品都给不了的体验。
2. **本期体验升级重点**：管理面从「演示级」到「运营级」——检索/筛选/批量操作（1000 用户 ≤ 3 次点击）、SU 自助改密、结构化错误信息（告别「连接失败」四字排查 20 分钟）。
3. **新设计面**：审计日志查询页、FinOps 用量大盘、身份源可视化配置页（角色映射免手写 JSON）——三块都是全新界面，Q1 起需要设计资源前置介入。
4. **里程碑节奏**：Q4 末审计可查可导出 → Q1 末成本可见可告警 → Q2 末身份好配、百级用户可运营 → Q3 末五合一导航收口。
5. **设计约束**：Q3 统一台重构会改变现有信息架构，届时需产出迁移指引；Q2 可用性切片「只增强不改结构」，设计稿以现有组件框架为基准。

## 七、附录：RICE 评分口径

- **Reach**（1-10）：受影响用户/场景广度，管理面核心项按「全部企业部署的管理员 + 采购决策者」计（8-9），身份生态按「国内政企占比」计（6-7）。
- **Impact**（1-3）：3=采购一票否决项解除或独占心智建立；2=显著效率/体验提升；1=内部工程质量。
- **Confidence**（0.6-0.9）：有 Commercial Issue 或多源交叉验证取 0.8+，推断型取 0.6-0.7。
- **Effort**（人月）：后端/前端/平台联合估算粗粒度值。
- RICE 仅做同季度内排序参考，季度间排序以 P0/P1/P2 战略框架为准（防守优先于进攻，进攻优先于还债）。
