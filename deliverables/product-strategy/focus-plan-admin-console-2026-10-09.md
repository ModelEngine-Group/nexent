# Nexent 管理面尖刀功能聚焦方案（第二轮规划）

- 日期：2026-10-09
- 作者：路径（Roadie）· 路线图规划师
- 任务：Task #8 —— 基于"做精不做广"战略转向，收敛尖刀功能组合并重排 2026 Q4–2027 Q3 路线图
- 输入：竞析《竞品尖刀打法研究》（2026-10-09）、瑞思《尖刀方向用户需求挖掘》（2026-10-09）、数析《管理面-core 集成断层分析》（2026-10-09）、第一轮路线图《roadmap-admin-console-2026-10-08.md》
- 决策基线：主理人三方交叉验证结论——尖刀组合 = 主轴 b「运行时治理台」+ 配套 c「知识库迁入」单点 + a 易用性转 P2 还债

## 一、战略转向声明：从"广度占位"到"单点做透"

第一轮路线图以"补齐审计/计量、一年逼近 L5"为主线，是**防守型广度规划**。产品负责人本轮战略转向：**不做广，做精——选少数尖刀功能打出竞争力**。竞析的成败案例研究给出明确判据：单点必须选在竞品**结构性无法跟进**的位置（n8n vs Zapier、RagFlow DeepDoc、LangSmith 控制台），而 Flowise/Langflow 证明"功能全但平庸"的终局是被收购或停运。

本轮规划遵循三条铁律：

1. **尖刀 ≤ 2 个**：主轴「运行时治理台」（结构性壁垒）+ 配套「Dify 知识库迁入器」（获客杠杆）。其余一切让路。
2. **尖刀不是另起炉灶**：治理台复用第一轮 Q4 审计+计量异步管道向上延伸，管道投资不浪费。
3. **验收对标"做透"而非"上线"**：治理台对标 LangSmith 的 trace 下钻体验，迁入器对标 Supabase 迁移工具的"5 分钟完成"标准。

**总叙事**："Dify 看不到的，Nexent 管理台直接看"（对照 Dify issue #42265：Agent V2 连执行日志 UI 都没有）+ "5 分钟从 Dify 把知识库搬进来"（趁 Coze 涨价、Dify 付费墙收紧、Flowise 停运的迁移窗口）。迁入（获客）+ 治理台（留存）一体化。

## 二、尖刀功能定义

### 尖刀 1（主轴）：运行时治理台（Runtime Governance Console）

**一句话定位**：开源 Agent 平台中唯一让管理员在管理台直接**看见并操控 core 运行时**的控制台——管得住沙箱、看得见事件、停得了任务、下得钻 trace。

**目标用户**：
- 主要：私有化部署的平台管理员/运维工程师（每部署 1–5 人，企业采购决策的关键影响者）
- 次要：排障中的 Agent 开发者（从管理面下钻 run 级细节，替代翻日志文件）
- 决策者：金融/医疗/政府场景的 IT 负责人（"平台方能看到每个 Agent 在干嘛"直接回应数据治理问询）

**功能构成**（数析断层清单 Top 3 + 分期子模块）：

| 模块 | 内容 | 期次 |
|---|---|---|
| 沙箱策略管理 | sandbox_policy 可视化配置 + 热生效 + 沙箱容器池监控 | v1（2027 Q1） |
| 运行时事件流 | 7 类预算裁决异常 + verification 失败明细 + guardrail 命中，统一落表+查询/筛选/告警 | v1（2027 Q1，管道 2026 Q4 预建） |
| 交互式运行视图 | 跨租户运行中 Agent 列表 / 详情 / 取消 | v1（2027 Q1） |
| 容量驾驶舱（子模块） | 模型并发/排队水位、lane 水位、成本关联视图（**只读一期**） | v2（2027 Q2） |
| Trace 下钻与重放 | run → LLM 调用参数/token/延迟 → 工具调用入参出参；失败 run 一键重放 | v3（2027 Q3） |

**容量驾驶舱取舍决策**：竞析提出其可作并列功能，本规划决定**收编为治理台子模块、分两期落地**——理由：① 每季度 3–4 人资源支撑不起三个尖刀并行；② 并发/lane 水位是进程级状态，多副本聚合需走 OTel 指标通道（数析断层 #4 标注难度"中"），只读一期风险可控、操控能力（熔断/降级开关）推迟 2027 Q4 评估；③ 它与原 Q1 FinOps 大盘天然合并为"算力与成本驾驶舱"，叙事上从"配额是配置文件"升级为"配额是方向盘"。

**对标竞品的"做透标准"验收线**：

| 验收项 | 做透标准（对标对象） | 判据 |
|---|---|---|
| 沙箱策略热生效 | 对标 Dify/Coze 的环境变量+重启方案，做其结构性做不到的 | 管理员在界面修改沙箱策略后**免重启、全租户 ≤2 分钟生效**（现状：改 9 个 NEXENT_SANDBOX_* 环境变量+重启进程）；策略变更 100% 进审计日志 |
| 事件流查询 | 对标 LangSmith trace 列表的筛选与下钻体验 | 7 类预算异常+验证失败可按租户/Agent/时间/类型四维筛选；从事件下钻到 run 上下文 **≤2 次点击**；事件产生到可查 **≤60 秒** |
| 运行视图操控 | 对照 Dify #42265（Agent V2 无执行日志 UI，社区称 "significant blocker"） | 管理员从跨租户运行列表定位任一运行中任务并取消，**≤3 次点击**；列表延迟 ≤10 秒 |
| Trace 下钻（v3，最终做透线） | 对标 LangSmith Trace Mode / LangGraph Studio time-travel | 从租户列表 → Agent → 某次 run 的 LLM 调用参数、token 成本、延迟、工具调用入参出参，**全程 ≤3 次点击且可截图演示**（wow moment 判据，竞析 1.3）；失败 run 可载入上下文改参数重跑 |
| 数据成本护栏 | 对照 Dify 执行明细存 DB 拖慢整体性能的翻车前例 | 汇总事件落 PG、明细 span 走 OTel 后端分层存储；治理台查询对业务库 P95 延迟影响 <5ms |

**依赖的 core 代码证据**（引自数析报告）：
- `sdk/nexent/core/agents/sandbox.py`（**3,206 行，core 最大单文件**）：管理面零入口；`management.py:1632 build_sandbox_policy()` 从 9 个 `NEXENT_SANDBOX_*` 环境变量组装，**DB 优先逻辑已存在但无任何写入入口**——只差一张配置表+表单
- `sdk/nexent/core/models/capacity_budget.py`（542 行）：已定义 **7 类结构化预算裁决异常**（ReserveExceedsCapacity / FingerprintMismatch / CallerMaxTokensOverrideForbidden 等），现无告警/日志界面
- `sdk/nexent/core/agents/verification.py:37`：`VerificationResult.to_payload()` 已是完整 JSON 载荷——**数据结构现成，只缺持久化和 UI**
- `backend/services/runtime_state_service.py`：Redis 多副本运行状态（run/cancel/stream 键结构）已在，多副本协调已解决——只补管理员查询/取消 API
- `sdk/nexent/core/monitor/`：OTel SDK 生产 Agent/Chain/LLM/Tool 四级 span + OTLP 指标，**生产端已存在、产品内零呈现**（monitoring_app 仅 2 路由外链 Grafana）
- 样板先例：`capacity_resolver.py` + `/suggest-capacity` API + ModelCapacityCoverageWidget（66 行）证明"core 深度能力翻译成管理面可视化"模式可行

**RICE**：9×3×0.8/12 ≈ **1.8**（Effort 大但全部是"接线"工程而非引擎研发；结构性壁垒使其竞争折损低，季度间排序以战略框架优先于 RICE 绝对值）

### 尖刀 2（配套）：Dify 知识库迁入器（KB Importer）

**一句话定位**：官方出品的"5 分钟把 Dify 知识库搬进 Nexent"工具——把竞品最大的资产壁垒变成 Nexent 的获客入口。

**目标用户**：
- 主要：正在考虑离开 Dify/Coze 的团队中的技术负责人/平台工程师（瑞思信号：Coze 涨价 39.9 元/月 + 免费额度砍至 10 credits/天；Dify SSO/审计/组织权限锁企业版；Flowise 2026.7 停运存量找出口）
- 特征：是**抢夺型需求**（竞品存量用户）而非存量用户呼声（Nexent 自有渠道尚无迁移 Issue）——需接受它面向拉新

**功能构成**：填 Dify API base + key → 自动拉取 datasets 列表 → 勾选要迁的知识库 → 自动拉取原始文档 → 走 Nexent data_process 链路重切片+统一 embedding → 产出导入完成报告（成功/失败/跳过明细 + 不支持项显性标注）。

**明确不做**（范围控制，详见 Non-goals）：不解析 Dify DSL、不做工作流转换、不直迁向量数据（业界共识向量不可跨平台迁移，重嵌入是唯一正解且成本可控）。

**对标"做透标准"验收线**：

| 验收项 | 做透标准（对标对象） | 判据 |
|---|---|---|
| 迁移耗时 | 对标 Supabase Heroku 迁移工具的 "migrate in a few clicks" | 50 文档 / 10 万字规模知识库：**人工操作 ≤5 次点击、人工参与时间 ≤5 分钟**，全程（含后台索引）≤15 分钟完成并出报告 |
| 预期管理 | 对标 Langflow 官方文档的诚实口径（"不要期待 1:1 自动迁移"）+ AgentBridge 的占位符显性化策略 | 导入前预检报告明示支持范围与不支持项；**不存在"静默失败"**——每个失败/跳过项有原因与建议动作 |
| 迁入即生产可用 | 差异化于 AgentBridge（DSL 转换器、以讯飞为中转）的核心主张 | 迁入的知识库立即可被 Agent 检索引用、可在治理台事件流中看到其 embedding/检索消耗（**私有化 + 无付费墙 + 迁移即可观测**完整链路） |
| 承接体验 | 瑞思风险提示：迁移者第一周因"日志不直观、报错模糊"二次流失 | 与尖刀 1 同期交付；模型/索引失败报错为结构化信息（状态码+原因+建议），非"连接失败"四字 |

**依赖的 core 代码证据**（引自数析报告）：
- `backend/apps/dify_app.py` + `backend/services/dify_service.py`（203 行）：已有 Dify datasets API 对接先例（httpx 客户端管理、连接/鉴权/限流错误码处理）——证明团队对接过 Dify API，起跳板现成
- `data_process` 导入链路：文档解析→切片→嵌入全流程现成，迁入器只需把"拉取 Dify 文档流"接到该链路头部
- `backend/services/repository_import_precheck.py`：六类依赖可用性预检（model/KB/embedding 维度/MCP/skill/tool）——预检报告 UI 的直接复用件
- 资产现状：Agent 导入导出（JSON/ZIP + 冲突检查）已是同类产品较完整实现（地基完成度约 45%），但知识库**无通用导出**是迁移场景最大缺口——本尖刀正是补这个缺口

**RICE**：7×3×0.7/5 ≈ **2.9**（Reach 按竞品存量迁移人群计；Confidence 0.7 因信号全部来自竞品社区、缺一手验证——已列风险与对冲）

### 非尖刀：易用性（方向 a）转 P2 还债

瑞思定性准确：易用性是**卫生因素（hygiene factor）**——不修流失存量，修好不构成获客。#3449（百级用户无检索/批量）、#3413（SU 无改密）维持第一轮排期（2027 Q2 最小切片），不占尖刀资源；结构化错误信息因同时是迁入器承接体验的依赖（成本低、收益高），提前至 2026 Q4 顺手交付。

## 三、与第一轮路线图的整合：四季度重排

**重排总览**：

```
2026 Q4「合规基座 + 治理台数据地基」 → 2027 Q1「尖刀主季：治理台 v1 + 知识库迁入」
→ 2027 Q2「算力成本驾驶舱 + 迁入增强 + 可用性还债」 → 2027 Q3「Trace 做透收口 + 身份补位 + 架构还债」
```

### 2026 Q4 —— 合规基座 + 治理台数据地基

**季度目标**：关掉 #2189，建成**一套**异步写入管道同时服务审计、计量、运行时事件三类数据（分开建必返工——这是把第一轮管道投资转化为尖刀地基的关键决策）；顺手交付结构化错误信息。

| 交付项 | 说明 | 备注 |
|---|---|---|
| 审计日志全套 | 沿用第一轮 Q4 规划不变（表/API/UI/CSV 导出/保留策略，四类最小事件集） | #2189 |
| Token/调用计量埋点 | 沿用第一轮规划（租户×用户×Agent×模型四维，埋点+落库不做界面） | 尖刀依赖 |
| **运行时事件管道（新增）** | capacity_budget 7 类异常 + verification to_payload() + guardrail 命中，统一落 `runtime_event_t`；与审计/计量共用异步批量写入；管道设计预留 trace 明细扩展位（明细走 OTel 后端不进 PG，只落汇总事件） | 尖刀地基，Q1 只需做 UI |
| **core 接口对齐（新增）** | 与 core 团队评审敲定：sandbox_policy 配置表结构（DB 优先逻辑已存在）、runtime_state_service 管理员查询/取消 API 契约、lane/并发指标 OTel 导出格式 | 数析建议的前置动作，防止 Q1 尖刀被接口分歧阻塞 |
| 结构化错误信息（提前项） | 模型连通性等高频失败场景报错含状态码+请求路径+建议 | 迁入器承接体验依赖 |
| **深访与内容营销验证（新增，非工程）** | 瑞思风险项：完成 3–5 个"正在考虑离开 Dify/Coze"目标团队深访；发布一篇《Dify→Nexent 知识库迁移实战》测试流量捕获 | Q1 迁入器投入深度的决策门槛 |

**季度目标**：治理台三大 v1 模块上线 + 知识库迁入器 GA，季末双叙事发版——这是本轮战略转向的兑现季。

## 四、资源假设与分配

**假设**：每季度 3–4 人工程资源（后端 1.5–2 人、前端 1 人、平台 0.5–1 人），无新增 headcount；core 团队按 Q4 敲定的接口契约提供评审支持（不计入本分配）。

| 季度 | 尖刀（含地基/收口） | 第一轮基线项（合规/配额/身份/重构） | 还债与卫生项 |
|---|---|---|---|
| 2026 Q4 | 30%（事件管道+core 接口对齐） | 55%（审计+计量） | 15%（结构化错误信息） |
| 2027 Q1 | **70%**（治理台 v1 + 迁入器） | 15%（配额最小版） | 15% |
| 2027 Q2 | 55%（驾驶舱+迁入增强） | 0% | 30%（#3449/#3413）+ 15% PoC（门槛制，未过门槛回填尖刀） |
| 2027 Q3 | 40%（Trace 做透） | 30%（OIDC/SSO） | 30%（统一台+组件重构） |
| **全年合计** | **≈50%** | **≈25%** | **≈25%** |

**解读**：尖刀全年占用约一半工程容量；Q1 是资源倾斜顶点（70%），Q2/Q3 逐步回落并归还身份与还债空间。第一轮的 P0（审计/计量）一分不减地保留在 Q4——它们既是企业门槛也是尖刀数据地基；被推迟的是 P1 身份纵深和 P2 重构，均有明确归位季度或评估触发条件。

## 五、Non-goals 更新（比第一轮扩充）

第一轮 8 项 Non-goals（billing、组织树、行级权限、SCIM、多环境治理、SIEM 实现、license 切分、2FA）**全部继续有效**，本轮新增以下 8 项：

| 项 | 决策 | 理由 |
|---|---|---|
| **Dify DSL 全量解析 / 工作流迁移** | 本期不做，2027 Q2 仅门槛制 PoC | 数析：差一个完整产品（DSL 解析器+字段映射+编排转换）；瑞思：Nexent 自有渠道零迁移 Issue；范围失控是最大工程风险 |
| **Coze 迁移** | 不做 | Coze 官方连工作流 YAML 导出都不支持（需社区 fork），源头资产拿不到，投入产出比差 |
| **跨平台 DSL 互转工具（AgentBridge 模式）** | 不做 | 讯飞已免费开源占位；军备竞赛无胜算。我们做"以 Nexent 为终点的官方迁入"，不做中转站 |
| **向量数据直迁** | 不做，产品内明示 | 瑞思/竞析一致确认：向量库绑定平台、embedding 与分块策略不同，跨平台向量不可迁移；重传原始文档+重嵌入是唯一正解。产品文案必须写明，管理用户期望 |
| **对话历史/运营数据迁移** | 不做 | 全行业无导出通道，随平台丢失是公认现状，不承诺 |
| **治理台实时操控强写能力**（限流熔断/降级开关/路由切换） | 2027 Q4 评估，本期容量驾驶舱只读 | 操控面涉及生产安全（误熔断=生产事故），只读先行积累水位数据与信任 |
| **产品内全量 OTel 观测栈替代 Grafana** | 不做 | 数析标注难度"高"（需查询/存储层）；只做 Trace 查看器 + 关键指标卡片，完整观测栈仍走外链，边界清晰 |
| **LangSmith 式 evals/评测平台** | 不做 | 观测≠评测；评测是另一条赛道（且已有专门玩家），不稀释尖刀 |

另：**国产身份扫码、RBAC 数据化、自定义角色**从第一轮 Q2/Q3 明确推迟至 **2027 Q4 评估**（非删除，需在利益相关者沟通中明示）。

## 七、利益相关者沟通要点（增量的部分）

**高管版**：战略从"补齐企业级门槛"升级为"单点做透"——用一年把「运行时治理台」做成开源界的 LangSmith（LangSmith 已验证该控制台可独立卖钱），用「知识库迁入器」趁 Coze 涨价/Dify 付费墙/Flowise 停运窗口抢夺存量。代价：身份生态与自定义角色推迟 2-3 个季度，需高管认可"集中兵力"的取舍。

**工程版**：Q4 三管合一（审计/计量/运行时事件共用异步管道）是全年最重要的架构决策，分开建必返工；治理台 90% 是"接线"工程（core 能力已存在，只缺管理面出口），Q4 必须完成与 core 的接口契约评审；分层存储（PG 汇总 + OTel 明细）是数据成本护栏。

**设计版**：治理台是五块全新界面（沙箱策略表单、事件流查询、运行视图、容量驾驶舱、trace 下钻树），Q1 起需要设计资源前置；trace 下钻树的信息密度对标 LangSmith，需要专门的信息设计投入。
